# 菜单数据实测发现

这些是跨 skill 通用的结论，来自对真实门店（1450713）的实测。做任何涉及"这个餐多少钱 / 多少热量"的判断前先读这个。

## 1. 卡价不是标价

`query-meals` 返回的 `currentPrice` 对有 `discountType` 的商品可能是**有条件的**：

| discountType | 含义 | 能否当标价 |
|---|---|---|
| 无（null） | currentPrice 即标价 | ✅ |
| `促销优惠` | 限时促销价，无需额外动作 | ✅ |
| `麦金卡优惠` / `早餐卡优惠` / `随单购…优惠` | **要先买卡** | ❌ |

实测：`全明星双人分享餐八件套` 标 `currentPrice 49.9` / `originalPrice 114.5`，带 `withOrder{membershipCode:"106", specId:"880"}` —— 49.9 是买麦金卡之后的价格。把它当标价会高估优惠。

真实门店的 124 项菜单里，**19 项**属于这一类。

## 2. 营养数据只覆盖 38% 的菜单

| 指标 | 数值 |
|---|---|
| 菜单总项数 | 124 |
| 有营养数据 | 47（38%） |
| 无营养数据 | 54（套餐 14 + 上新单品 40） |
| 卡价排除 | 19 |
| 周边/非食品 | 3 |

营养表 `list-nutrition-foods` 是 **160 行的静态表**，收录经典单品（巨无霸、麦辣鸡腿汉堡、薯条、可乐…）。菜单上的套餐和当季新品基本不在表里。

**后果**：任何"热量/蛋白质"结论，都必须声明它只覆盖菜单的一部分。不要对未收录的商品给数字。

## 3. `query-meal-detail` 不给营养，部分求和会骗人

这个工具返回的是**套餐组成**（rounds → choices 的 code / name / diffPrice / isDefault / modification），**没有任何热量或蛋白质字段**。

所以不能用它给套餐补营养。更危险的是只对上一部分：

`龙焰鸡腿堡三件套`（9900016073）拆解后：
- 龙焰鸡腿堡（主堡）→ 营养表里**没有**
- 中薯条（4810）→ 289 kcal ✅
- 可乐中杯（3050）→ 147 kcal ✅

把能对上的加起来是 436 kcal，而真实值约 950 —— **少了整个汉堡**。这种数字比不给数字更糟，因为它看起来像是算出来的。

**规则**：套餐里只要有一个子项营养未知，就不给这个套餐的总热量。

## 4. 营养表的结构特征

- 没有 `productCode`，只能靠中文名匹配
- 有重名：`小杯玉米杯`、`纯牛奶（盒装）` 各出现两次，同名取首行
- 全角/半角括号混用：营养表 `纯牛奶（盒装）` vs 菜单 `纯牛奶(盒装)`
- 尺寸类商品缺省后缀：菜单 `可乐` vs 营养表 `可乐中杯` / 可乐大杯 / 可乐小杯
- 口味变体不可猜：菜单 `派` vs 营养表 `香芋派` / `菠萝派`

## 5. 价格才是有 100% 覆盖的数据

124 项菜单每一项都有 `currentPrice`，每个渠道都报得出价。任何依赖"菜单全覆盖"的判断，都应该建立在价格上，而不是营养上。
